# 静止中の再描画停止・gltfpack 1.3 更新・中間LOD 設計

## 背景

660MB級のSTEP（部品 約9,800・精密版の三角形 約868万）を、内蔵グラフィックスのタッチパネルPCで表示すると、精密版の1フレームに約0.25秒かかる（実測 4fps）。操作中は軽量版（`_lod.glb`、元の5%）に切り替えている（2026-07-14-interaction-lod-design.md）。

2026年11月時点の調査では、ブラウザで使える根本的に新しい手段（クラスタLOD、WebGPU）は見当たらなかった。ただし、次の3点に改善の余地がある。

1. `animate()` が、静止中も精密版を毎フレーム描き直している。そのため、触った瞬間に描画途中の重いフレームを待つことになり、発熱と電力も無駄になる
2. gltfpack 1.3 で、簡略化時に頂点の位置と属性を整え直すオプション `-sv` が追加された
3. 操作中は5%版しかないため、性能に余裕のある機械や軽いモデルでも、操作中の見た目が粗い

## ゴール

- 静止中は描き直さない。触ったときと、表示が変わったときだけ描く
- gltfpack を 1.3 に更新する。`-sv` は軽量版と中間版にだけ付ける（比較して効果があれば）
- 操作中はまず中間版（約15%）を出す。中間版の描画が遅い機械では、そのモデルの間は5%版に自動で下げる
- 既存の変換済みモデル（`_mid.glb` を持たない）は、今までどおり動く

## スコープ外

- 精密版（`モデル.glb`）の圧縮設定の変更。静止時の見た目は変えない
- 既存モデルの一括再変換
- 下げた段階を、同じモデルを表示している途中で中間版に戻すこと

## 1. 描画オンデマンド（viewer/src/viewer.js）

`requestAnimationFrame` のループは続ける（`controls.update()` は慣性と自動回転のために毎フレーム必要）。ただし、`renderer.render()` と `frameCallbacks`（注釈の位置更新など）は、次のどれかに当てはまるフレームだけ実行する。

- カメラ位置か注視点が前フレームから動いた（既存の `moved` 判定。慣性と展示モードの自動回転もここに含まれる）
- 描画要求の期限内である。`requestRender(ms)` で「今から ms ミリ秒は描き続ける」と予約する

描画要求を出すのは次の場面。

- `document` で `pointerdown` / `pointermove` / `pointerup` / `wheel` / `keydown` / `click` を、capture 段階で受けたとき（0.5秒）。UIボタンによる部品の色・表示・稜線・テーマの変更も、すべてクリックを起点にしているため、個別に呼ばなくても拾える
- モデル・軽量版・中間版の読み込み完了、窓の大きさの変更、精密版と軽量版の切り替え（`applyInteractionQuality`）。いずれも1回描く
- `requestRender` を export し、クリック以外を起点にした非同期の変更（サーバーからの注釈読み込みなど）からも呼べるようにする

純粋ロジック `createRenderScheduler()`（`request(ms, now)` / `shouldRender(moved, now)`）を `lod.js` に置き、単体テストする。

FPSカウンター（診断表示）は、描画したフレームだけを数える。静止中は更新が止まるが、意図どおりの動きである。

## 2. gltfpack 1.3（converter/bin/gltfpack.exe）

- 公式の GitHub Releases から、Windows 版の gltfpack 1.3 を入手して差し替える（入手の前にユーザーの許可を取る）
- `compress_glb_lod`（5%）と、新しく作る `compress_glb_mid`（15%）に `-sv` を付ける。付けるかどうかは、見本STEPで `-sv` あり・なしを変換し、三角形数と見た目（スクリーンショット）を比べて決める。効果が無い、または不具合があれば付けない
- `compress_glb`（精密版）は今の引数のまま

## 3. 中間LOD

### 変換ツール（converter/src/compress.py, pipeline.py）

- `compress_glb_mid(src, dst)` を追加する。引数は `-cc -si 0.15 -sa`（＋採用するなら `-sv`）。`-kn` は付けない（軽量版と同じく、部品の選択はしない）
- `convert()` は、軽量版の生成のあとに `<stem>_mid.glb` を作る。失敗しても変換全体は成功扱いにし、中間版だけを飛ばす（軽量版と同じ方針）
- 統計（部品数・三角形数・サイズ）は、今までどおり精密版だけを数える

### ビューア

- `modelsource.js` の `modelPaths` に `mid: /models/{name}_mid.glb` を追加する
- `models-api.js` は、一覧から `_mid.glb` も除く
- `main.js` は、精密版 → 軽量版 → 中間版の順に読み込む。中間版の取得や読み込みに失敗しても無視する
- `viewer.js` は、中間版を `buildLodBatches` で組み立てて、精密版の子として持つ（`midGroup`）
- 操作中に表示するのは、中間版があり、まだ下げていなければ中間版、それ以外は軽量版
- **自動で下げる判定**：純粋ロジック `createTierGovernor({ slowMs: 66, samples: 10 })` を `lod.js` に置く。中間版を表示している間のフレーム間隔を記録し、直近10フレームの中央値が 66ms（約15fps）を超えたら「下げる」と判定する。判定は1回だけで、以後はずっと下げたままにする。中間版を出した直後の1フレーム目は、切り替えの重さを含むので数えない
- 下げたら `midGroup` を取り外して `dispose()` し、メモリを空ける
- 新しいモデルを読み込んだら、判定の状態を初期化する
- 軽量版が無く中間版だけある場合は、下げずに中間版を使い続ける

## テスト

- viewer（vitest）：`createRenderScheduler`、`createTierGovernor`、`modelPaths` の mid、models-api の `_mid` 除外
- converter（pytest）：`compress_glb_mid` が引数どおりに gltfpack を呼ぶこと、`convert()` が `_mid.glb` を出すこと、中間版の生成に失敗しても変換は成功すること
- 実機確認：開発サーバー（ポート4001）で見本モデルを開き、静止中に描画が止まること（FPSカウンター）、操作中に中間版が出ること、描画を遅くしたときに軽量版へ下がることを確かめる
- 変換ツールの EXE を作り直して起動を確かめる
